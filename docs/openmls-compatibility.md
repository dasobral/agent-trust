# OpenMLS 0.9.0 compatibility gate

**Decision: blocked for the exact LAP-MLS binding.** OpenMLS `0.9.0` provides the ordinary MLS operations needed by the approved agent-trust profile, but its public API cannot construct or expose the required stripped KeyPackage preimage before the final MLS signatures. The implementation must therefore not start the real MLS binding until an upstream API addition or a maintained fork with a tested pre-signing API provides that hook. An outer certificate sidecar does **not** satisfy this gate.

## Candidate and feature boundary

- Candidate: [`openmls` 0.9.0](https://docs.rs/openmls/0.9.0/openmls/), released as upstream tag [`openmls-v0.9.0`](https://github.com/openmls/openmls/releases/tag/openmls-v0.9.0).
- Use the normal, non-draft API: `openmls = { version = "=0.9.0", default-features = false }`. The crate feature table has no `default = [...]` entry; this spelling makes the empty default feature set explicit. Do not enable `virtual-clients-draft`, `test-utils`, or `extensions-draft` for the compatibility claim. The virtual-client feature is explicitly separate and pulls in `extensions-draft` ([manifest](https://github.com/openmls/openmls/blob/openmls-v0.9.0/openmls/Cargo.toml#L45-L113)).
- A type-only executable gate compiled successfully against that exact dependency set with Cargo offline. It exercised `KeyPackageBuilder` extension inputs, GroupContext/LeafNode extension types, standalone Remove and GroupContextExtensions proposals, forced-path commits, AAD, public frontier access, and `MlsGroup::load`. It did not enable any OpenMLS optional feature.

## Matrix

| Contract requirement | Status | Public API evidence and implementation consequence |
|---|---|---|
| Custom `acc_context` in GroupContext | **Supported** | `MlsGroup::builder().with_group_context_extensions(Extensions<GroupContext>)` is public ([source](https://github.com/openmls/openmls/blob/openmls-v0.9.0/openmls/src/group/mls_group/builder.rs#L352-L358)). `Extension::Unknown(u16, UnknownExtension)` carries application bytes and `Extensions::single/from_vec` validates the placement ([source](https://github.com/openmls/openmls/blob/openmls-v0.9.0/openmls/src/extensions/mod.rs#L325-L390), [validation constructor](https://github.com/openmls/openmls/blob/openmls-v0.9.0/openmls/src/extensions/mod.rs#L466-L486)). The adapter must define the TLS payload and reject wrong/absent values; OpenMLS preserves unknown data but does not interpret ACC semantics. |
| Custom `authz_incarnation` in LeafNode | **Supported** | The group builder accepts `Extensions<LeafNode>` ([source](https://github.com/openmls/openmls/blob/openmls-v0.9.0/openmls/src/group/mls_group/builder.rs#L360-L369)); `LeafNodeParameters` supplies replacement extensions on a self-update ([rustdoc](https://docs.rs/openmls/0.9.0/openmls/treesync/struct.LeafNodeParameters.html)). Capabilities and required-capabilities validation remain an adapter admission rule. |
| Custom KeyPackage extension | **Supported as an extension slot** | `KeyPackageBuilder` accepts both KeyPackage and LeafNode extensions before `build` ([source](https://github.com/openmls/openmls/blob/openmls-v0.9.0/openmls/src/key_packages/mod.rs#L518-L611)). This is sufficient for a non-cyclic application value. It does **not** supply the required APF pre-sign workflow below. |
| APF signs the stripped KeyPackage preimage before final LeafNode/KeyPackage signatures | **BLOCKER** | The actual `KeyPackageTbs` and its `unsigned_payload()` are private ([source](https://github.com/openmls/openmls/blob/openmls-v0.9.0/openmls/src/key_packages/mod.rs#L153-L176)); `KeyPackage` also keeps its payload and signature private ([source](https://github.com/openmls/openmls/blob/openmls-v0.9.0/openmls/src/key_packages/mod.rs#L179-L185)). The only public construction path is a one-shot builder `build`, while the internal `KeyPackage::create` that generates key material and signs is `pub(crate)` ([source](https://github.com/openmls/openmls/blob/openmls-v0.9.0/openmls/src/key_packages/mod.rs#L282-L305), [builder finalization](https://github.com/openmls/openmls/blob/openmls-v0.9.0/openmls/src/key_packages/mod.rs#L604-L620)). A placeholder KeyPackage cannot be amended with the APF certificate and re-signed through public API. Required upstream/fork capability: a stable two-phase KeyPackage/LeafNode TBS API that (1) creates the final key material and exposes canonical stripped bytes, (2) accepts the APF certificate extension, and (3) performs the final MLS signatures. |
| Standalone external Remove proposal | **Supported** | With `virtual-clients-draft` disabled, `ExternalProposal::new_remove` constructs an external Remove; the member method `MlsGroup::propose_remove_member` is a distinct API ([source](https://github.com/openmls/openmls/blob/openmls-v0.9.0/openmls/src/group/mls_group/proposal.rs#L434-L449)). The generic standalone proposal API is also public ([source](https://github.com/openmls/openmls/blob/openmls-v0.9.0/openmls/src/group/mls_group/proposal.rs#L220-L236)). The adapter must process and validate the proposal before accepting it into the APF-selected commit. |
| Standalone external GroupContextExtensions proposal | **Supported** | `ExternalProposal::new_group_context_extensions` constructs an external GroupContextExtensions proposal; the member method is a distinct API ([source](https://github.com/openmls/openmls/blob/openmls-v0.9.0/openmls/src/group/mls_group/proposal.rs#L572-L595)). |
| Exact removal followed by a regular Commit with UpdatePath | **Supported** | `CommitBuilder::propose_removals` builds exact removal proposals and `force_self_update(true)` forces a path ([source](https://github.com/openmls/openmls/blob/openmls-v0.9.0/openmls/src/group/mls_group/commit_builder.rs#L284-L323)). Path computation occurs when the force flag is set ([source](https://github.com/openmls/openmls/blob/openmls-v0.9.0/openmls/src/group/mls_group/commit_builder.rs#L849-L870)). The convenience `remove_members` path is also a regular builder commit ([source](https://github.com/openmls/openmls/blob/openmls-v0.9.0/openmls/src/group/mls_group/membership.rs#L213-L248)). Use the builder form so the adapter can require the qualifying policy-binding proposal in the same canonical commit. |
| Persistent OpenMLS state provider and restart loading | **Supported at the trait/API level; provider durability still needs an integration test** | `StorageProvider` requires writing group configuration, tree, context, group state, and message secrets ([source](https://github.com/openmls/openmls/blob/openmls-v0.9.0/openmls_traits/src/storage.rs#L29-L132)); `MlsGroup::load` reconstructs a group from those persisted entries ([source](https://github.com/openmls/openmls/blob/openmls-v0.9.0/openmls/src/group/mls_group/mod.rs#L497-L534)). Pin a durable provider separately and test crash/restart semantics. This is not the KeyPackage-hook blocker. |
| Set authenticated data on the exact outgoing ciphertext | **Supported** | `MlsGroup::set_aad(Vec<u8>)` applies to the next outgoing message and is reset only after a successful `MlsMessageOut` ([source](https://github.com/openmls/openmls/blob/openmls-v0.9.0/openmls/src/group/mls_group/mod.rs#L326-L336)). The adapter must set `H(release certificate)` immediately before the one allowed application-message creation. |
| Canonical MLS frontier: group, epoch, tree hash, confirmed transcript hash | **Supported** | `MlsGroup::public_group().group_context()` is public ([source](https://github.com/openmls/openmls/blob/openmls-v0.9.0/openmls/src/group/mls_group/mod.rs#L926-L929)); `GroupContext` exposes group ID, epoch, tree hash, confirmed transcript hash, and extensions ([source](https://github.com/openmls/openmls/blob/openmls-v0.9.0/openmls/src/group/group_context.rs#L189-L216)). Do not rely on the separately feature-gated `MlsGroup::tree_hash()` helper. |
| Retained-state adversary | **Test arrangement supported; end-to-end result unverified** | The adversary model is a byte-for-byte retained copy of the selected durable provider before the removal, not an OpenMLS helper API. The proposed provider contract persists tree/context/secrets, and `MlsGroup::load` provides the restart side. The future laboratory must copy that provider state, apply the qualifying removal/UpdatePath to honest copies, and show the retained removed copy cannot process a successor application message. This requires the pinned provider and a real multi-client test. |

## Required gate outcome

The real MLS laboratory remains **not yet capable of the exact LAP-MLS certificate binding** on OpenMLS 0.9.0. A compatible upstream release or a maintained fork must expose the two-phase KeyPackage preimage/final-signature workflow and then pass an end-to-end test that verifies the APF certificate binds the exact canonical stripped preimage inside the MLS object. No outer sidecar, post-hoc hash, or reconstructed look-alike may be substituted for that binding.

Primary source correction: external-sender construction is implemented in `openmls/src/messages/external_proposals.rs` (`ExternalProposal::new_remove` and `new_group_context_extensions`), not the member proposal methods originally cited above. The type-only gate checked member APIs; external-sender end-to-end behavior remains unverified.
