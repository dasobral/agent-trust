# OpenMLS 0.9.0 compatibility gate

**Decision: the staged KeyPackage gate passed with the maintained fork, and the LAP-MLS coupling is verified in the laboratory profile (see [`lap-mls.md`](lap-mls.md)).** The project pins custom fork commit `6daabe33ddb616a6ed54b511d333e691db18a99f`. It exposes the stripped KeyPackage preimage before the final outer signature, and it recomputes that preimage structurally from a validated final KeyPackage. The laboratory embeds and verifies an APF-signed admission certificate in the final KeyPackage. This is not an outer sidecar.

## Candidate and feature boundary

- Baseline: [`openmls` 0.9.0](https://docs.rs/openmls/0.9.0/openmls/), released as upstream tag [`openmls-v0.9.0`](https://github.com/openmls/openmls/releases/tag/openmls-v0.9.0).
- Integrated fork: [`dasobral/openmls@6daabe33`](https://github.com/dasobral/openmls/commit/6daabe33ddb616a6ed54b511d333e691db18a99f), branch `agent-trust/keypackage-staging-v0.9`.
- Use the normal, non-draft API. Do not enable `virtual-clients-draft`, `test-utils`, or `extensions-draft` for the compatibility claim.
- A type-only executable gate compiled successfully against that exact dependency set with Cargo offline. It exercised `KeyPackageBuilder` extension inputs, GroupContext/LeafNode extension types, standalone Remove and GroupContextExtensions proposals, forced-path commits, AAD, public frontier access, and `MlsGroup::load`. It did not enable any OpenMLS optional feature.

## Matrix

| Contract requirement | Status | Public API evidence and implementation consequence |
|---|---|---|
| Custom `acc_context` in GroupContext | **Verified in the laboratory** | `src/mls.rs` places an APF-signed `acc_context` (`0xf043`: group, policy revision, `(subject, generation)` roster) in the GroupContext at creation and in every bound commit through a GroupContextExtensions proposal. `RequiredCapabilities` lists it. Every member checks coherence after a merge and before its durable COMMIT (`tests/lap_mls.rs`): forged, rolled-back, or roster-incoherent bindings are rejected and roll back. |
| Custom `authz_incarnation` in LeafNode | **Verified in the laboratory** | The KeyPackage leaf carries an APF-signed `authz_incarnation` (`0xf044`: group, subject, generation, leaf signature key). It is set before `prepare`, so the staged admission certificate also covers it, and UpdatePath preserves it (`LeafNode::update` keeps extensions by default). The coherence check requires every leaf's incarnation to match its credential and key, and the leaf multiset to equal the `acc_context` roster. |
| Custom KeyPackage extension | **Supported by the fork** | The staged `prepare` / `with_external_binding` / `finalize` flow freezes the canonical KeyPackage preimage, embeds the APF binding, and then signs the finished KeyPackage. |
| APF signs the stripped KeyPackage preimage before the final KeyPackage signature | **Verified in the laboratory** | The fork freezes all public material and the leaf signature in `prepare`, exposes canonical stripped `KeyPackageTBS` bytes, inserts exactly one opaque top-level binding extension, and creates the final outer signature in `finalize`. `agent-trust` independently validates and canonicalizes the final KeyPackage, checks the embedded certificate fields and preimage digest, and verifies its APF Ed25519 signature before Add. |
| Standalone external Remove proposal | **Supported** | With `virtual-clients-draft` disabled, `ExternalProposal::new_remove` constructs an external Remove; the member method `MlsGroup::propose_remove_member` is a distinct API ([source](https://github.com/openmls/openmls/blob/openmls-v0.9.0/openmls/src/group/mls_group/proposal.rs#L434-L449)). The generic standalone proposal API is also public ([source](https://github.com/openmls/openmls/blob/openmls-v0.9.0/openmls/src/group/mls_group/proposal.rs#L220-L236)). The adapter must process and validate the proposal before accepting it into the APF-selected commit. |
| Standalone external GroupContextExtensions proposal | **Supported** | `ExternalProposal::new_group_context_extensions` constructs an external GroupContextExtensions proposal; the member method is a distinct API ([source](https://github.com/openmls/openmls/blob/openmls-v0.9.0/openmls/src/group/mls_group/proposal.rs#L572-L595)). |
| Exact removal followed by a regular Commit with UpdatePath | **Supported** | `CommitBuilder::propose_removals` builds exact removal proposals and `force_self_update(true)` forces a path ([source](https://github.com/openmls/openmls/blob/openmls-v0.9.0/openmls/src/group/mls_group/commit_builder.rs#L284-L323)). Path computation occurs when the force flag is set ([source](https://github.com/openmls/openmls/blob/openmls-v0.9.0/openmls/src/group/mls_group/commit_builder.rs#L849-L870)). The convenience `remove_members` path is also a regular builder commit ([source](https://github.com/openmls/openmls/blob/openmls-v0.9.0/openmls/src/group/mls_group/membership.rs#L213-L248)). Use the builder form so the adapter can require the qualifying policy-binding proposal in the same canonical commit. |
| Persistent OpenMLS state provider and restart loading | **Verified in the laboratory (receiving-member crash only)** | Each durable endpoint uses the fork's `openmls_sqlite_storage` (one rollback-journal SQLite file per endpoint, `serde_json` codec). Every MLS operation is one `BEGIN IMMEDIATE … COMMIT` transaction. `tests/mls_durable.rs` restarts a member from its file through `MlsGroup::load` and `SignatureKeyPair::read`, and it then decrypts traffic it had not processed before the restart and signs as itself. A receiving member that crashes after OpenMLS writes the successor epoch but before COMMIT reloads the complete previous epoch and then processes the redelivered commit. The crash is simulated by closing the connection with the transaction open; hot-journal recovery after a hard process kill is not exercised. A committer crash between commit creation and COMMIT (protect/persist/emit ordering) is not covered here. |
| Set authenticated data on the exact outgoing ciphertext | **Supported** | `MlsGroup::set_aad(Vec<u8>)` applies to the next outgoing message and is reset only after a successful `MlsMessageOut` ([source](https://github.com/openmls/openmls/blob/openmls-v0.9.0/openmls/src/group/mls_group/mod.rs#L326-L336)). The adapter must set `H(release certificate)` immediately before the one allowed application-message creation. |
| Canonical MLS frontier: group, epoch, tree hash, confirmed transcript hash | **Supported** | `MlsGroup::public_group().group_context()` is public ([source](https://github.com/openmls/openmls/blob/openmls-v0.9.0/openmls/src/group/mls_group/mod.rs#L926-L929)); `GroupContext` exposes group ID, epoch, tree hash, confirmed transcript hash, and extensions ([source](https://github.com/openmls/openmls/blob/openmls-v0.9.0/openmls/src/group/group_context.rs#L189-L216)). Do not rely on the separately feature-gated `MlsGroup::tree_hash()` helper. |
| Retained-state adversary | **Verified in the laboratory** | `tests/mls_durable.rs` takes a byte-for-byte copy of a member's quiescent SQLite file (no open transaction, no journal) before its removal and opens it in a fresh connection outside the roster. The copy decrypts old-epoch traffic, which shows it is a complete state. It is rejected on successor traffic after the qualifying removal and UpdatePath, while continuing members, including one restarted after the removal, still decrypt. |

## Required gate outcome

*Historical (pre-fork) gate text:* The real MLS laboratory remains **not yet capable of the exact LAP-MLS certificate binding** on OpenMLS 0.9.0. A compatible upstream release or a maintained fork must expose the two-phase KeyPackage preimage/final-signature workflow and then pass an end-to-end test that verifies the APF certificate binds the exact canonical stripped preimage inside the MLS object. No outer sidecar, post-hoc hash, or reconstructed look-alike may be substituted for that binding. The maintained fork has since satisfied this gate.

Primary source correction: external-sender construction is implemented in `openmls/src/messages/external_proposals.rs` (`ExternalProposal::new_remove` and `new_group_context_extensions`), not the member proposal methods originally cited above. The type-only gate checked member APIs; external-sender end-to-end behavior remains unverified.
